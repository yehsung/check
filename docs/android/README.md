## 이 폴더의 규칙

- **확률 숫자를 쓰지 않는다**(G §2-3 W6-c ①, E §9.4).
  - 뽑기 확률은 서버 값이다. 서버가 바꾸면 등록정보가 그날부터 거짓이 된다.
  - 기호만이 아니다. 'N프로', 'M번에 N번', 'M분의 N', 'N in M', 1보다 작은 소수 같은 꼴도 쓰지 않는다. 확률 낱말(확률·당첨·odds·chance)이 든 문장에는 숫자를 두지 않는다(절 번호·버전·`1:1` 은 뺀다).
  - 이 규칙을 설명하는 이 문단에도 실제 숫자를 쓰지 않았다. 검사기가 여기도 잰다.
  - "앱 안 [확률 보기] 에서 공개한다"까지만 적는다.
  - 같은 이유로 가격·판돈 수령액·상금처럼 서버가 바꾸는 숫자도 등록정보 본문에 박지 않는다.
  - 스크린샷에도 [확률 보기] 시트를 넣지 않는다.
- **자격증명·연락처·계정 이메일을 쓰지 않는다.** 저장소가 공개다.
  - 데모 계정 이메일·비밀번호와 지원 이메일은 콘솔에만 입력한다.
  - 이 문서에는 `<콘솔에만 입력>` 같은 자리표시자만 둔다.
- **콘솔에 옮길 칸에 낡은 문장을 옮기지 않는다**(G §2-3 W6-c ②).
  - 칸은 여섯이다: 앱 이름 · 간단한 설명 · 자세한 설명 · 출시 노트 · 영어 지시문 둘.
  - 금지 목록 한 벌을 여섯 칸 모두에 건다. 영어 문구는 [app-access.md](app-access.md) §3, 한국어 문구(길건너·역대·아이폰·도전 미션 …)는 [store-listing.md](store-listing.md) §3.3 에 있다.
- 검사기: `python3 -I docs/android/_check/check_listing.py`
  - 잰다: 확률 숫자, 자격증명·이메일·긴 계정 번호, 글자 수 한도, 여섯 칸의 낡은 문장과 꼭 있어야 할 문구, Data safety·IARC 표와 E §9.3·9.5 의 일치.
  - Data safety·IARC 는 **글자로** 비교한다. 기대값은 설계 E 표의 원문 글자다. IARC 답 칸도 E 글자 그대로라서, 뜻을 뒤집거나 덧붙인 답은 빨갛다.
  - `--self-test`: 규칙마다 결함 표본을 문서 사본에 심고, **바로 그 규칙**이 잡는지 잰다. 규칙 이름 목록도 고정해 둔다. 그래서 규칙 하나를 지우거나 망가뜨리면 self-test 가 빨갛다.
  - `--e-source <설계 E 파일>`: 검사기의 기대값이 설계 E §9.3·§9.5 원문 표와 같은지 잰다. 설계서가 저장소 밖이라 CI 는 돌리지 않는다. E 를 고친 뒤 사람이 돌린다.
  - `_check/` 는 밑줄로 시작한다. 그래서 GitHub Pages(Jekyll)가 이 폴더를 사이트로 내보내지 않는다. 마크다운 문서도 머리말 `published: false` 로 같은 효과를 낸다.

## 제출 순서 (G §4-1 콘솔 항목과 같은 순서)

1. 처리방침 URL 이 열리는지 확인한다 → [app-content.md](app-content.md) §1
2. 웹 계정 삭제 URL 이 실제로 열리는지 확인한다(죽은 링크도 위반 — E §9.9 (d)) → [app-content.md](app-content.md) §2
3. 데이터 보안 → [data-safety.md](data-safety.md)
   - 소속 센터는 '개인 정보 › 기타 정보' 행으로 신고한다(G §8-19 #3 — §2 표에 반영, 검사기 `G_DATA_SAFETY_ADDS`).
4. 콘텐츠 등급(모의 도박 '아니오' — 사용자 결정 2026-10-30, 아이폰과 같게. G §8-19 #6①)
   - 제출 전에 지역별 결과(특히 GRAC)를 본다.
   - 자세한 것은 [content-rating.md](content-rating.md).
5. 앱 액세스 → [app-access.md](app-access.md)
   - iOS 숨김 심사 계정을 재사용한다.
   - 자격증명은 콘솔에만 넣는다.
6. 광고·대상 연령·기타 선언 → [app-content.md](app-content.md) §3~§5
7. 스토어 등록정보 → [store-listing.md](store-listing.md)
   - 제출 직전 "실제 빌드와 대조" 표를 한 줄씩 확인한다.
8. 사전 출시 보고서를 끄고 관리형 게시를 켠다 → [app-content.md](app-content.md) §6

## 이 초안이 기대는 사실과 결정

- Android 첫 판의 기능 바닥은 iOS 1.0.14 다(G §8-16, §8-18 #7).
  - 길건너 아잉이(crossy)와 역대 순위 [오늘|역대] 전환은 넣지 않는다.
  - 판돈 대결의 신청·수락 진입은 `appConfig.duelsEnabled` 가 켜진 빌드에서만 보인다.
  - 깃발이 꺼진 빌드는 내부 테스트 트랙에만 오른다(G §8-17 #1).
  - 그래서 **심사를 받는 트랙(비공개·프로덕션)의 빌드에는 대결이 있다**고 보고 썼다.
- 처리방침의 Android 절은 main `4cf98bf` 에 올라가 있다. 이 갈래 기준선 `0ab5789` 에는 아직 없다.
  - 웹 계정 삭제 페이지도 같은 커밋에 있다.
  - Data safety 답은 그 처리방침 문장과 대조했다([data-safety.md](data-safety.md) §4).
- 서버 표·칸은 메인 체크아웃의 마이그레이션 141개(서버 ①~③ 반영)를 읽어 확인했다. 운영 서버에는 접속하지 않았다.
